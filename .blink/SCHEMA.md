# Blink format reference

Generated by `blink init`. This file is the field reference for the tracker in
this repository — read it before writing or editing anything under this
directory. It is documentation only: nothing reads it at runtime, and editing it
changes nothing about what is validated.

The authority is `blink validate`. Run it after every write.

## Shape

One markdown file per entity. YAML frontmatter is **state**; the body is
free-form prose — the **thinking**. The directory a file sits in determines its
type.

    project.md                    the project overview
    SCHEMA.md                     this file
    milestones/m-01-slug.md
    tasks/t-0001-slug.md
    decisions/d-001-slug.md
    risks/r-001-slug.md
    docs/some-slug.md
    runs/x-0abc12-slug.md

## Three structural rules

1. **Frontmatter `id` is authoritative.** The filename *should* match
   `<id>-<slug>.md`. A mismatch is a warning, not an error — the file still
   loads, keyed by its frontmatter `id`.
2. **Forward references only.** A task points at its milestone; a milestone
   never lists its tasks. A task points at the risk blocking it; a risk never
   lists what it blocks. Every reverse index is computed. This is a concurrency
   rule wearing the clothes of a style rule: forward-only means adding or moving
   a task touches exactly one file, so two writers never contend on the same
   file and a merge stays a merge. A run is the one carve-out — it lists the
   tasks it covers — and it is legitimate because a run record is single-writer
   by construction: the orchestrator is the only thing that writes it while the
   run is on, so the contention this rule defends against cannot arise.
   Inverting it, a `run:` field on each task, would make every lane dispatch
   and every state change mutate a task file, manufacturing exactly that
   contention in the one workflow where many lanes are in flight at once. A run
   is a log, not a taxonomy: a task belongs to one milestone permanently, which
   is why that pointer is intrinsic to the task, while a task appears in several
   runs across retries, and that sequence is history worth keeping rather than a
   field to overwrite. Recorded as `d-0bl3lm`.
3. **Fixed status enums, validated.** There are no per-project vocabularies.
   Anything outside the lists below is an error.

## Filename rules

| Type | Filename | Notes |
|---|---|---|
| Milestone | `milestones/<id>-<slug>.md` | |
| Task | `tasks/<id>-<slug>.md` | |
| Decision | `decisions/<id>-<slug>.md` | |
| Risk | `risks/<id>-<slug>.md` | |
| Run | `runs/<id>-<slug>.md` | Written by the executor, not by hand |
| Doc | `docs/<id>.md` | **Exactly the id.** No numeric prefix, no extra slug |
| Project | `project.md` | Leave `id` out of the frontmatter; it defaults to `project` |

For the first five, `<id>.md` on its own is accepted too — it is the `-<slug>`
that is optional, never the id. A doc named `docs/<id>-<slug>.md` is a filename
warning, and a `project.md` whose frontmatter carries any `id` other than
`project` is the same warning.

## Ids

New ids for the five numbered types are **timestamps, not counters**: seconds
since `2026-01-01T00:00:00Z` (epoch constant `1767225600`), encoded lowercase
base36 and left-padded with `0` to exactly six characters, behind the type
letter — `t-0bj4qz`, `m-0bj4qz`. A run's letter is `x` because `r` is the
risk, and `e` is left free for a later type. Generate one with `blink id t`
(or `m`, `d`, `r`, `x`), or without Blink installed:

    node -e 'console.log((Math.floor(Date.now()/1000)-1767225600).toString(36).padStart(6,"0"))'

Never allocate an id by counting up from the highest existing one — two writers
on different clones both find the same "next" number and collide at merge.
Timestamp ids collide only when two writers create the same entity type in the
same literal second, and `blink validate` still catches that residual case.
Padding keeps lexicographic order equal to creation order, so id sorting stays
chronological. Legacy sequential ids (`t-0001`, `m-01`) stay valid forever and
are never renumbered; doc ids are slugs and are unaffected.

## Every entity carries

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | **yes** | Unique within its type |
| `title` | string | **yes** | |
| `status` | enum | **yes** | Per type, below |
| `created` | day or timestamp | no | Prefer a timestamp |
| `updated` | day or timestamp | no | Bump it on every write. Prefer a timestamp |
| `tags` | string[] | no | Defaults to `[]` |

`created` and `updated` take either a `YYYY-MM-DD` day or a full ISO 8601
timestamp with a zone — `2026-08-14T10:30:00Z` or `2026-08-14T16:00:00+05:30`.
**Write a timestamp.** Agents touch this tracker several times an hour, and at
day resolution a task created, started and finished before lunch records the
same string three times: "sort by recently updated" cannot order it and
`blink drift` cannot tell whether a commit came before or after the task
describing it. A day is still accepted and always will be, so nothing already
written needs changing.

Every stored timestamp ends up with a zone, one way or another. Write one and it
is kept. Leave it off an **unquoted** value and YAML settles it for you: a bare
`2026-08-14T10:30:00` is a YAML timestamp scalar, which the spec defines as
UTC, so it is read back as `2026-08-14T10:30:00.000Z`. Leave it off a
**quoted** value — `"2026-08-14T10:30:00"` — and it is rejected, because a
quoted string is not a timestamp scalar and nothing has said what moment it
means. Writing the `Z` yourself sidesteps the whole distinction.

Milestone `start`, `target` and `original_target`, and a decision's
`date`, stay days and reject a time: a target is a day you are aiming at, not
a moment.

Dates must be real. `2026-02-31` has the right shape and is rejected, with or
without a time on the end, and so is `T25:00:00Z`. Unquoted YAML dates are
fine — `updated: 2026-08-11` is read back as the string `2026-08-11`.

## Task — `tasks/t-NNNN-slug.md`

`status`: `backlog` | `planned` | `in_progress` | `blocked` | `paused` | `done` | `dropped`

| Field | Type | Required | Notes |
|---|---|---|---|
| `milestone` | milestone id | no | Absent or unknown → grouped as "no milestone" |
| `owner` | string | no | Agent name or human name; matched against discovered agents |
| `blocked_by` | id[] | **required when `status: blocked`** | Risk ids or task ids |
| `paused_reason` | string | **required when `status: paused`** | Resuming clears it; never carry it forward |
| `archived` | boolean | no | Only legal on `done` or `dropped`; hides the card by default |
| `decisions` | decision id[] | no | Decisions this task implements |
| `docs` | doc id[] | no | Related docs |
| `estimate` | string | no | Free text (`2d`, `S/M/L`). Displayed, never computed with |
| `order` | number | no | Sort within a column. Absent → sorts by id, after every explicit order |

The lifecycle runs `backlog` → `planned` → `in_progress` → `done`, with three
exits: `dropped` (cancelled, terminal), `blocked` (external dependency, requires
`blocked_by`), and `paused` (voluntary hold, requires `paused_reason`). A task
is created at `backlog` while the work is still being planned — the file exists
from the moment the work is thought of, not from the moment someone starts it —
and moves to `planned` once it is planned and queued. Nothing is ever deleted;
abandoned work is `dropped`, which keeps the history and takes it out of the
progress denominator.

`paused` is a resumable hold: it can return to `in_progress`, go back to
`planned`, or be cancelled as `dropped`. It is not terminal.

A task with `status: blocked` and an empty `blocked_by` is an **error**; a task
with `status: paused` and no `paused_reason` is the same. Both name a state that
cannot be acted on without their companion field.

## Transition map

Legal status transitions — a jump not in this map is a drift warning (history
may be squashed), not a validation error:

| From | To |
|---|---|
| `backlog` | `planned` \| `dropped` |
| `planned` | `in_progress` \| `backlog` \| `dropped` |
| `in_progress` | `done` \| `blocked` \| `paused` \| `dropped` |
| `blocked` | `in_progress` \| `paused` \| `dropped` |
| `paused` | `in_progress` \| `planned` \| `dropped` |
| `done` | *(terminal)* |
| `dropped` | *(terminal)* |

## Milestone — `milestones/m-NN-slug.md`

`status`: `planned` | `active` | `done` | `dropped`

There is no `in_progress` here — that is the **task** enum. A milestone being
worked on is `active`. Every type's enum stands alone; borrowing a value from
another type's list is an error, not a warning.

| Field | Type | Required | Notes |
|---|---|---|---|
| `order` | number | no | Sequence on the Timeline and Overview |
| `start` | date | no | Timeline bar start |
| `target` | date | no | Timeline bar end |
| `original_target` | date | no | Drawn as a dashed ghost bar, so slips stay visible |
| `summary` | string | no | One line for the Overview |

Never list a milestone's tasks here. Tasks point at milestones.

Set `original_target` **once**, the first time `target` moves, and then leave it
alone. It records where the plan started, not where it was last.

`status`: `proposed` | `accepted` | `superseded`

| Field | Type | Required | Notes |
|---|---|---|---|
| `date` | date | no | When it was decided |
| `supersedes` | decision id[] | no | Points backwards at older decisions only |

Body convention: `## Context` / `## Options` / `## Decision` / `## Consequences`.

## Risk — `risks/r-NNN-slug.md`

`status`: `open` | `mitigated` | `accepted` | `closed`

| Field | Type | Required | Notes |
|---|---|---|---|
| `severity` | `low` \| `medium` \| `high` | **yes** | Drives Overview ordering |

Body convention: `## Impact` / `## Mitigation`. Tasks reference risks through
`blocked_by`; a risk never lists what it blocks.

## Doc — `docs/<id>.md`

`status`: `draft` | `active` | `superseded`

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | string | **yes** | The slug. The filename must be exactly `<id>.md` |
| `type` | `brainstorm` \| `note` \| `research` \| `spec` | **yes** | |
| `supersedes` | doc id[] | no | Docs supersede docs, never decisions |

## Run — `runs/x-NNNNNN-slug.md`

`status`: `planned` | `running` | `blocked` | `done` | `abandoned`

One execution of a work set already in the tracker: which tasks it covers, in
which tier, behind which gates, and where each lane got to. Runs are written by
the executor and `blink run`, **not by hand** — a run is a record of what an
orchestrator did, and hand-editing one mid-run fights the process writing it.
This is the type the rule 2 carve-out covers: a run lists its tasks because it
is single-writer by construction.

| Field | Type | Required | Notes |
|---|---|---|---|
| `tier` | `inline` \| `subagents` \| `orchestrators` \| `ask` | **yes** | How the run was executed. Shares the project's `orchestration` enum |
| `tasks` | task id[] | no | The tasks this run covers, in dispatch order |
| `gates` | string[] | no | Confirmed gate commands, in run order |
| `lanes` | lane[] | no | One row per dispatch — fields below |
| `blocked_reason` | string | **required when `status: blocked`** | Why the run stopped |

Each `lanes` row:

| Field | Type | Required | Notes |
|---|---|---|---|
| `task` | task id | **yes** | Must appear in this run's `tasks` |
| `worktree` | string | no | Worktree root, absolute. Absent for the inline and subagent tiers |
| `branch` | string | no | The lane's branch |
| `state` | `pending` \| `dispatched` \| `ready` \| `merged` \| `failed` \| `skipped` | **yes** | |
| `attempts` | number | no | Failed dispatches so far. Defaults to `0` |
| `wave` | number | **yes** | Which wave dispatches this lane. Never guessed |

The body is the confirmed pre-flight plan followed by an append-only event log.

## Project — `project.md`

`status`: `active` | `paused` | `done` | `archived`

| Field | Type | Required | Notes |
|---|---|---|---|
| `started` | date | no | |
| `orchestration` | `inline` \| `subagents` \| `orchestrators` \| `ask` | no | How fan-out work is executed. Absent = `ask` |

Leave `id` out. The body is the project overview.

## What validation says

`blink validate` exits `0` when there are no errors — warnings alone still exit
`0`, which is what makes it usable in CI and as a self-check after every write.

**Errors** (exit 1): unparseable YAML; a status outside its enum; a missing
`id`, `title` or `status`; a missing `severity` on a risk or `type` on a doc;
a date that is not a real calendar day; `status: blocked` with no `blocked_by`;
`status: paused` with no `paused_reason`; a run at `status: blocked` with no
`blocked_reason`; a `lanes[]` entry naming a task the run does not list;
`archived: true` on any status other than `done` or `dropped`; two files of the
same type sharing an `id`; a content directory that is not there at all.

**Warnings** (exit 0, still worth fixing): a filename that does not match its
`id`; a markdown file loose in this directory instead of an entity
subdirectory — only `project.md`, `SCHEMA.md` and `README.md` may sit at the
top level; a `milestone`, `blocked_by`, `decisions`, `docs` or `supersedes`
reference to an id that does not exist; a run's `tasks` reference to an id that
does not exist.

Nothing is ever dropped silently. A file that fails its schema is still listed,
in an `invalid` bucket, with the reason.

## Derived values, never written down

Milestone progress is `done / (total - dropped)` over the tasks pointing at it;
project progress is the same over all tasks. Blocked counts, open risks and
in-flight-by-agent are all computed. Do not write any of them into a file.
